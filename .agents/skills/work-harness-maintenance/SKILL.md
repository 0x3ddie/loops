# Maintain the personal harness

Start at `~/.agents/harness/README.md` and `manifest.json`. The canonical work standard is `CORE.md`; selected skill sources live in `~/.agents/skills/`. Application copies are generated by `scripts/sync.py`.

## Audit

Run the sync script without `--apply` for a read-only check. Inspect actual discovery paths and current official product documentation before changing adapters. A file present on disk is not proof that an application's current session loaded it.

Compare installed capabilities before adding a skill. Watch for duplicate names, overly broad triggers, conflicting instructions, unnecessary approval loops, and references to unavailable tools. Do not remove or update unrelated plugins as part of this harness.

## Update

1. Establish the requested change and inspect the current source, provenance, local adaptations, and destination drift.
2. For an upstream update, resolve a specific commit and download it into a fresh staging directory outside skill discovery. Read the changed instructions and any scripts, hooks, or dependencies before activating them.
3. Preserve upstream notices and record the repository, path, commit, checked date, hashes, and local changes in the manifest/source register. Never describe a modified copy as pristine upstream.
4. Edit canonical sources. Preserve user intent and existing authorization; do not introduce mandatory approval for ordinary already-authorized work.
5. Validate skill frontmatter and referenced resources. For changed helper scripts, exercise the relevant failure and preservation behavior in a temporary home directory. `validation/test_sync.py`, `test_loop.py`, and `test_writing.py` cover synchronization, experiment records, and mechanical prose checks. Run the tests relevant to the change.
6. Run `scripts/sync.py --apply`, then the read-only check. The synchronizer refuses to overwrite independently edited destination files; inspect and reconcile such edits first.

Updates are manual and evidence-driven. Do not schedule background updates or execute remote installers merely because a new upstream release exists. Do not silently overwrite local preferences.

For a substantive instruction change, use representative tasks and actual outputs to compare the old and new behavior. Include factual preservation, task completion, unnecessary questions, and formatting. Keep coding correctness and research quality as guardrails when tightening prose. Check the assistants and models actually used; a good result on one does not establish the others. Record unrun behavioral checks explicitly. Add recurring failures to the regression cases instead of stacking untested global rules.

## Recovery

Each synchronization that changes files records exact pre-change bytes and a receipt under `~/.agents/harness/backups/`. Consult the README before restoring. Preserve any work made after the backup.

Report source/format validation separately from in-app discovery and behavioral checks. Use the smoke prompts in `validation/SMOKE-PROMPTS.md` when runtime access is available; do not claim they were run if they were only documented.
