The system improves one measured bottleneck at a time. Each experiment starts with a user outcome, a reproducible baseline, a minimum useful gain, and checks for quality, correctness, and cost. Those choices stay fixed during the experiment. If the benchmark changes, a new run establishes a new baseline.

The working sequence is baseline, candidate, review, controlled release, field observation, and regression protection. A promising candidate goes through a review of the measured revision and a PR when shipment is in scope. The release stays behind a flag where the project supports one. If field evidence supports the gain, tighten the regression limit with enough headroom for normal variation. If performance or quality regresses, disable the experiment and verify recovery before trying again. Inconclusive results consume a bounded observation allowance and never count as success.

This is a small graph with evidence required at each transition. It follows published Anthropic practices for incremental work, durable progress, evaluation, and feedback; the exact states and checks are our design. The [source notes](research/ANTHROPIC-WORKFLOW.md) distinguish their published guidance from our choices. There is no claim that this reproduces Anthropic's private process or shipping speed.

The new [work-improvement-loop skill](../skills/work-improvement-loop/SKILL.md) owns this workflow. Its helper records the contract, measurements, decisions, and artifact hashes under the project's `.agent-work/loops/` directory. It rejects skipped stages, mismatched revisions, altered evidence, and speed gains that fail required checks. A release checkpoint is saved before deployment, so an interruption leaves a visible obligation to inspect the provider and reconcile the result. A new chat can resume from this record.

The assistant still uses the project's actual benchmark, Git, deployment, flag, and telemetry tools. The helper does not deploy, call models, or start background jobs. Existing authorization remains valid. Candidate limits and a deadline bound experimentation; recovery remains possible after the deadline. An offline run finishes as a local result. A production claim requires field evidence from real sources. Submitted reports and hashes cannot prove that someone measured honestly, so evidence review remains necessary.

Writing is part of acceptance. Conversations use plain paragraphs by default, with no decorative headings, bold labels, stock enthusiasm, artificial contrasts, or repeated conclusions. Lists and tables remain available when they convey real structure. The [Humanizer writing contract](../skills/humanizer/references/output-contract.md) requires factual completeness and preserves the user's voice. Its checker catches selected formatting and phrase problems; the agent must also inspect meaning, uncertainty, and support for claims. No universal length limit can substitute for that review.

The global standard routes measured optimization to this skill across Codex, Claude Code, and Cursor. To use it, ask: “Use work-improvement-loop to reduce this project's slowest measured user flow. Establish the baseline, protect correctness, and work within the deployment permissions already given.” The agent then fills the contract with actual project facts. A simple edit continues to use the ordinary workflow.

Harness changes follow the same evidence principle: compare representative tasks before retaining a new instruction, preserve task quality, and check each assistant you use. The [validation record](validation/RESULTS.md) separates helper tests from application and model behavior. The mechanics have been tested with synthetic evidence; real gains must be demonstrated on an actual project.
